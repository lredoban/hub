TL;DR — On construit une lib open source (MIT) qui génère et valide des factures Factur-X, plus une API payante de validation. Le client est le dev d'un éditeur SaaS français, coincé par la deadline du 1er septembre 2026 et l'amende passée à 50 €/facture (plafond 15 k€/an). La lib gratuite est le vendeur ; l'API et la veille normative encodée sont le revenu. 15 jours de build, npm publié à J8.

Les 5 pièges métier qui structurent tout le code

  1. Un avoir n'est pas une facture négative. TypeCode 381 avec montants positifs — l'erreur n°1 des devs, encodée en test.
  2. L'arrondi TVA se fait par groupe de taux, jamais par ligne. Sinon des écarts d'un centime qui font rejeter la facture.
  3. MINIMUM/BASIC WL ne sont pas des factures fiscales complètes. Warning systématique — ne jamais laisser un client croire qu'il est en règle.
  4. Le modèle interne est sémantique (BT-x), pas syntaxique. CII et UBL ne sont que des sorties.
  5. Jamais de float. Montants en centimes entiers ou Decimal, de bout en bout.

Ce que le moteur décide (et refuse de décider)

  • 4 verdicts : PASS, PASS_WITH_WARNINGS, FAIL, et surtout INDETERMINATE — le moteur refuse de conclure (PDF chiffré, UBL non couvert en V1, extensions EXTENDED) plutôt que produire un faux verdict.
  • generate recalcule toujours les totaux lui-même ; si l'appelant en fournit qui divergent, il refuse. Jamais de correction silencieuse.
  • Chaque erreur = message français actionnable (quoi, où, combien, comment corriger) — ce mapping règle→message est l'actif propriétaire.
  • API stateless : aucune facture stockée — argument RGPD/sécurité qu'un gros SaaS ne peut pas donner.
À ne jamais promettre — « conformité garantie », du conseil fiscal, l'archivage probant, la transmission DGFiP (on n'est pas une PDP), une validation PDF/A « certifiée ». Obligation de moyens dans les CGV.

MVP — 15 jours

V1 : lib core (profils BASIC + EN 16931) → embed PDF/A-3 → validation Schematron + 20 règles FR → CLI → API + Stripe → validateur web gratuit (la machine à leads). Simulé à la main au début : revue expert à 149 €, conversion UBL, veille par email. Interdit avant les premiers paiements : dashboard, e-reporting, connecteurs PDP, app Shopify (c'est Facturia, plus tard, sur cette lib).

Ordre : J1-2 calculs · J3-4 génération CII validée contre le validateur FNFE · J5 PDF · J6-7 validation + messages · J8 npm v0.1 publié quoi qu'il arrive · J9-10 API · J11 validateur web · J12-15 docs, CI croisée (FNFE + Mustang), landing branchée.

Moat solo-dev

  • MIT : core, PDF, CLI — devenir la lib TS par défaut = distribution gratuite permanente.
  • Payant : API hébergée, règles FR, fraîcheur (à jour ≤ 2 semaines après chaque release normative — un abonnement à la veille encodée en tests).
  • Source de vérité : publier la suite de conformité (les 55 tests) et inviter les autres libs à s'y mesurer. Celui qui écrit les tests écrit le standard de facto.

Validation commerciale — 30 jours

10 prospects nommés (Obat, Tolteck, Freebe, Abby, Henrri, Facture.net, modules PrestaShop, intégrateurs Odoo, SaaS verticaux, réseau Kompa). Script ≤ 90 mots dont l'arme : « sinon, gardez la lib, elle est MIT ». Pilote « Conforme avant le 1er septembre » : 1 490 € + 12 mois d'API. API : 29/99/299 €/mois, −50 % early-bird.

Validé si : ≥ 3 pilotes payés ou ≥ 10 abonnements ; ≥ 4 prospects sur 10 confirment l'urgence en call ; validateur ≥ 200 fichiers analysés. Invalidé si ≥ 6/10 répondent « notre PDP gère le format » → pivot Facturia ou Veillance.
